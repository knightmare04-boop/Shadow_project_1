## Where the Council Agrees

**DB-level triggers for financial invariants (b) are unambiguously the right call.** Every advisor who addressed it — Contrarian, First Principles Thinker, Expansionist, Executor — independently endorsed enforcing double-entry balance, period-close, and audit-log immutability at the Postgres trigger level rather than in application code. The reasoning converges exactly: the guarantee that matters is "true regardless of which code path writes," and only a DB-level constraint survives a bad migration, a raw psql session, or a future service that bypasses the API. No advisor argued for moving this logic into application code.

**The k6 test proves less than the write-up implies.** Contrarian, First Principles Thinker, Outsider, and Executor all independently identified the same methodology gap: 30 *distinct* idempotency keys against one invoice never exercises the SETNX claim/replay layer at all — it only proves the row lock and partial unique index correctly block concurrent *different*-key attempts. The layer the test is named for (idempotency) is the one layer it doesn't test. Three advisors (Contrarian, Outsider, Executor) also converged on the specific untested failure mode: a process crash between the Redis SETNX claim and the DB commit — with no answer given for whether the claim is leased/TTL'd or left to hang.

**(c) and (g) are the same problem, not two problems.** Once surfaced by the Executor and validated in every single peer review (Contrarian, First Principles Thinker, Expansionist, Outsider all separately named this as the standout insight of the round), this became a council-wide agreed fact: the online scorer holds one live `WindowGraph`/`LapMemory` instance in process memory, which means the 8.18s p95 collapse at 500 VUs cannot be fixed by adding a worker pool — multiple workers would each hold divergent, unsynchronized graph state. Scaling and correctness are coupled here in a way the original design decisions don't surface on their own.

**Pickle-based state crosses a real trust boundary.** Outsider, Executor, and First Principles Thinker converged (from different angles — CWE-502, `Unpickler.find_class` allowlisting, "confirm it never crosses a trust boundary") that "we control the writer" is an assumption, not a proof, and that the parity test (batch vs. online, 20k transactions) has never actually validated a save→restart→restore→continue cycle, which is the scenario pickle risk and correctness risk both hinge on.

**Shared Redis is a real but bounded risk.** All five agree cache-eviction pressure on a shared Redis instance could theoretically expire a live idempotency key early. Where they differ is severity (see below), but nobody disputes the fix is trivial: `noeviction` policy or a separate keyspace/instance for idempotency keys, and nobody could confirm from the write-up which policy is actually set.

## Where the Council Clashes

**The Expansionist vs. everyone else, categorically.** This is the sharpest and most consequential split in the whole exercise — not a disagreement about a technical fact, but about what a review is for. The Expansionist reframed nearly every identified gap as either a non-issue ("not a gap, that's the test under-selling what's proven") or a business opportunity ("package the trigger-proof suite as a standing compliance-evidence artifact"), and for question (g) — explicitly "the single highest-priority fix" — it declined to name a fix at all, answering instead with "don't fix a flaw." Every one of the other four advisors, reviewing anonymously and independently, flagged this same response as the weakest in the round, using strikingly similar language ("advocacy, not review," "marketing copy wearing review clothes," "reads as promotional... fails the review's actual purpose"). This is about as close to unanimous censure as five independent reviewers get, and it should be weighted accordingly: treat the Expansionist's optimism as noise on every question, especially (e), (f), and (g).

**How to sequence the fix for (g).** The Contrarian and the Outsider both read the 8.18s p95 result as "fix the deployment topology first" — real ASGI worker pool, proper pool sizing, real ingress instead of `host.docker.internal:8000` — treating it as a conventional ops problem. The Executor's response, which every peer review subsequently endorsed as the sharper diagnosis, shows that prescription doesn't actually work here: you cannot `--workers 4` your way out of this because scorer state lives in one process, so the conventional fix is blocked until state is externalized. This isn't a minor wording difference — the Contrarian/Outsider fix, applied naively, would not resolve the underlying problem. The council's own peer review effectively resolves this clash in the Executor's favor.

**Severity of the shared-Redis risk.** First Principles Thinker and Executor frame Redis eviction as a "client-experience" problem, not a ledger problem, because layers (b)/(c) — the row lock and the partial unique index — are the real correctness backstop and would still catch a duplicate even if the idempotency key evicted early. The Outsider frames it more sharply as an open, unverified finding ("that's the actual finding") because the write-up never states the `maxmemory-policy`. Both are compatible readings, but they imply different urgency — the Outsider's framing is closer to right: the *severity* is bounded by (b)/(c), but the *unknown* itself (what policy is actually configured) is still a finding worth resolving today, not a theoretical worry.

## Blind Spots the Council Caught

These are things no single advisor response raised, which only surfaced because the peer-review pass forced the advisors to look at each other's coverage rather than just answer the prompt:

- **The backup/restore drill's self-disclosed flaw (design decision #8) was ignored by all five advisors, in their primary responses.** The prompt itself states the fingerprint methodology isn't MVCC-safe without `pg_export_snapshot()` and is unsafe to run against live traffic — a named, unresolved risk that nobody engaged with directly. Two independent peer reviews (Contrarian, Outsider) flagged this same omission.
- **Nobody asked what happens when Redis is fully unavailable, not just evicting.** Given that design decision #1 calls Redis SETNX "correctness-critical," this is a real gap: does the idempotency middleware fail open (duplicate payments become possible) or fail closed (all payments blocked)? Caught only in the First Principles Thinker's peer review, not in any primary response.
- **No advisor asked whether the 0.005 PR-AUC gap from excluding TGN (#4) is monitored.** On a system whose entire premise is fraud detection, nobody asked whether the online model is shadow-scored against the offline champion to catch real missed fraud from that known accuracy gap. Caught only in the Outsider's peer review.
- **Whether the DEFERRABLE constraint trigger was ever proven through the real FastAPI/SQLAlchemy commit path, versus only "direct SQL transaction tests" as the prompt states.** There's a gap between what was proven and what production actually runs through connection pooling and ORM session boundaries. Caught only in the Executor's peer review.
- **Fraud scoring has no DB-level backstop the way payments do.** If the single scorer process dies, detection silently stops — there's no trigger, lock, or reconciliation sweep equivalent for the fraud-detection path the way there is for payments. Caught only in the Executor's peer review.
- **Every finding in this entire round is analytical inference, not an executed test.** Despite this system's own stated ethos being empirical proof over assertion (k6 load tests, direct SQL transaction tests, 20k-transaction parity replays), not one advisor reports having actually run the kill -9 crash test, the same-key concurrent-replay test, or a restart-then-restore parity test they all recommend — they reason about outcomes in prose. Caught only in the Expansionist's peer review, and it is the single most damning observation in the entire exercise precisely because it indicts the review process itself, not just the system.

## The Recommendation

This system's core financial-integrity design is sound and should not be re-architected: DB-level triggers for double-entry balance, period-close, and audit-log immutability are the correct call and the single strongest asset in the build, and the layered payment defense is mostly well-conceived even though the flagship k6 test doesn't prove what it's presented as proving. Do not let the Expansionist's framing — that the system is fundamentally fine at this scale and the remaining work is packaging, not fixing — carry any weight; the anonymous peer review unanimously rejected that framing, and the specific, falsifiable gaps every other advisor found (SETNX untested, single-process scorer state, pickle trust boundary, bcrypt truncation, PgBouncer/DEFERRABLE interaction, shared-Redis eviction policy unconfirmed) are real and checkable, not hypothetical.

The system is **not** ready for real production use. Not because any one layer is broken, but because the two things that would actually break it in production — the single-process scorer ceiling and the untested crash/restart paths — are exactly the things the current test suite structurally cannot see, and the council's own meta-finding (nobody actually ran the adversarial tests they recommend) means the confidence level implied by "verified via k6" and "proven with direct SQL tests" is higher than what has actually been demonstrated for the failure modes that matter most.

## The One Thing to Do First

**Externalize the online scorer's state (`WindowGraph`/`LapMemory`) out of single-process memory before attempting to scale the server at all.** This is the one fix the council converged on as structurally prerequisite to everything else in the performance story: adding a worker pool or fixing deployment topology (the Contrarian's and Outsider's instinct) will not resolve the 8.18s p95 collapse and may make correctness worse, because multiple workers would each hold their own divergent, unsynchronized graph state. Begin this work with the two cheap, concrete validation tests every advisor called for but nobody ran — a kill -9 chase test on the idempotency claim path, and a save→crash→restore→continue parity test on the pickled `LapMemory` state — since both are fast to execute and will tell you, empirically rather than by inference, exactly how much state-externalization work is actually required before this system can run behind more than one process.
